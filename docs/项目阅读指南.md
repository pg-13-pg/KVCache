# KVstorageBaseRaft-cpp 项目阅读指南

这份文档的目标不是替代源码注释，而是回答一个更实际的问题：第一次打开这个项目时，应该按什么顺序读，读每一层时要抓住什么主线，哪些文件先精读，哪些文件先略读。

项目主线可以先记成一句话：

客户端 `Clerk` 把 `Get/Put/Append` 请求发给某个 `KvServer`，`KvServer` 把请求包装成 `Op` 提交给本机 `Raft`，`Raft` 通过选举和日志复制让多数节点达成一致，提交后的日志通过 `applyChan` 回到 `KvServer`，最后由跳表状态机真正执行 KV 操作。

## 0. 先建立全局印象

建议先读这几个文件，不要一开始钻进所有 `.cpp`：

1. `README.md`
   了解项目背景、模块划分和作者希望你关注的重点。核心结论是：Raft 是主菜，RPC、协程、跳表、持久化都是支撑。

2. `docs/目录导览.md`
   对照仓库目录建立第一张地图。

3. `CMakeLists.txt`、`src/CMakeLists.txt`、`example/raftCoreExample/CMakeLists.txt`
   搞清楚目标文件、库文件、示例程序和依赖关系。

4. `src/raftRpcPro/raftRPC.proto`、`src/raftRpcPro/kvServerRPC.proto`
   先看协议定义，后看生成代码。`.pb.h/.pb.cc` 是 protoc 生成文件，第一遍不要精读。

## 1. 推荐的运行入口

项目主要示例入口在 `example/raftCoreExample`：

```bash
mkdir -p cmake-build-debug
cd cmake-build-debug
cmake ..
cmake --build . -j
```

启动一个多节点 KV/Raft 集群：

```bash
../bin/raftCoreRun -n 3 -f test.conf
```

再开一个终端运行客户端：

```bash
../bin/callerMain
```

注意：当前 `RpcProvider::Run` 里写节点地址时硬编码写入 `test.conf`，所以示例启动参数最好也使用 `-f test.conf`，否则服务端读的配置文件和 RPC 写出的配置文件可能不一致。

## 2. 项目模块地图

### `src/raftCore`

这是项目最核心的模块。

- `include/raft.h`：Raft 节点的全部核心状态和对外接口。
- `raft.cpp`：选举、日志复制、提交、apply、快照、持久化恢复。
- `include/kvServer.h`、`kvServer.cpp`：Raft 上层的 KV 服务，负责客户端 RPC、去重、等待日志提交、执行状态机、制作快照。
- `include/Persister.h`、`Persister.cpp`：Raft 状态和快照的文件持久化。
- `include/ApplyMsg.h`：Raft 向 KV 层交付已提交日志或快照的消息结构。
- `include/raftRpcUtil.h`、`raftRpcUtil.cpp`：Raft 节点间 RPC stub 的薄封装。

第一遍阅读优先级：

`raft.h` -> `kvServer.h` -> `raft.cpp::init` -> `Raft::Start` -> `Raft::doElection` -> `Raft::AppendEntries1` -> `Raft::sendAppendEntries` -> `KvServer::PutAppend/Get` -> `KvServer::ReadRaftApplyCommandLoop`。

### `src/raftClerk`

客户端模块。

- `include/clerk.h`：客户端保存所有服务端连接、客户端 ID、请求序号、最近 leader。
- `clerk.cpp`：`Get/Put/Append` 的重试逻辑。
- `include/raftServerRpcUtil.h`、`raftServerRpcUtil.cpp`：客户端到 KV 服务端 RPC stub 的薄封装。

阅读重点是：客户端请求失败或遇到 `ErrWrongLeader` 时，会轮询下一个服务端；同一个请求重试时 `RequestId` 不变，服务端通过 `ClientId + RequestId` 做幂等处理。

### `src/raftRpcPro`

Raft 和 KV 的 protobuf 协议定义与生成代码。

- `raftRPC.proto`：Raft 节点间的 `RequestVote`、`AppendEntries`、`InstallSnapshot`。
- `kvServerRPC.proto`：客户端访问 KV 服务的 `Get`、`PutAppend`。
- `*.pb.h`、`*.pb.cc`：生成文件，知道字段和 service 会变成 C++ 类即可。

第一遍只精读 `.proto`，不要从生成文件开始。

### `src/rpc`

项目自实现 RPC 框架，基于 protobuf service/stub 和 muduo 网络库。

- `rpcheader.proto`：RPC 框架自己的请求头，包含 service 名、method 名和参数长度。
- `mprpcchannel.cpp`：客户端侧统一打包 RPC 请求并通过 socket 发送。
- `rpcprovider.cpp`：服务端注册 protobuf service，解析请求头，反序列化参数，调用本地 service 方法，再发送响应。
- `mprpccontroller.cpp`：RPC 失败状态记录。
- `mprpcconfig.cpp`：读取 `key=value` 配置文件。

阅读时抓住一条线：

`protobuf Stub 调用` -> `MprpcChannel::CallMethod` -> 网络发送 -> `RpcProvider::OnMessage` -> `service->CallMethod` -> 被注册对象重写的 RPC 方法。

### `src/skipList`

上层 KV 状态机目前使用跳表实现。

- `include/skipList.h`：跳表模板类，支持插入、更新、查找、删除、dump/load。

对理解 Raft 来说，这一层可以先当成普通 KV 存储。二刷时再看 `dump_file/load_file` 如何服务于快照。

### `src/fiber`

协程与 IO 调度模块。

- `fiber.hpp/cpp`：基于 `ucontext` 的协程对象。
- `scheduler.hpp/cpp`：N-M 协程调度器。
- `iomanager.hpp/cpp`：基于 epoll 和定时器的 IOManager。
- `hook.cpp`、`fd_manager.cpp`、`timer.cpp`：系统调用 hook、fd 状态、定时器管理。

在当前 Raft 代码里，`Raft::init` 会创建 `monsoon::IOManager`，并调度 `leaderHearBeatTicker` 和 `electionTimeOutTicker`；`applierTicker` 仍使用独立线程。

第一遍读项目时，协程模块只需要知道“它用来跑定时循环”。等主线通了，再回来看协程实现。

### `src/common`

公共工具。

- `config.h`：心跳间隔、选举超时、apply 间隔、调试开关等。
- `util.h/cpp`：`DEFER`、断言、格式化、随机选举超时、阻塞队列 `LockQueue`、客户端命令 `Op`、错误码。

这里有两个关键类型：

- `LockQueue<T>`：类似 Go channel，用于 Raft 和 KV 层之间传递 `ApplyMsg`，也用于按 raft index 等待请求提交。
- `Op`：KV 层提交给 Raft 的命令，包含 `Operation/Key/Value/ClientId/RequestId`，使用 Boost serialization 转成字符串放进 Raft log。

### `example`

示例代码。

- `example/raftCoreExample/raftKvDB.cpp`：集群启动入口，会 fork 多个 `KvServer` 子进程。
- `example/raftCoreExample/caller.cpp`：客户端调用入口。
- `example/rpcExample`：单独学习 RPC 框架的最小示例。
- `example/fiberExample`：单独学习协程/IOManager 的示例。

### `test`

这里不是完整单元测试体系，更像作者验证语言特性或小功能的 scratch 文件。

- `test/run.cpp`：Boost 序列化实验。
- `test/defer_run.cpp`：`DEFER` 宏实验。
- `test/format.cpp`：格式化/断言实验。

## 3. 第一条主线：客户端请求如何变成一致提交

从 `example/raftCoreExample/caller.cpp` 开始：

1. `Clerk::Init("test.conf")`
   读取服务端节点地址，给每个节点创建 `raftServerRpcUtil`。

2. `Clerk::Put/Get/Append`
   构造 protobuf 请求，优先发给 `m_recentLeaderId`，失败就轮询下一个节点。

3. `raftServerRpcUtil::PutAppend/Get`
   通过 protobuf stub 调用远端 `kvServerRpc`。

4. `MprpcChannel::CallMethod`
   把 service 名、method 名、参数长度、参数内容打包后通过 TCP 发送。

5. `RpcProvider::OnMessage`
   服务端解析 RPC 请求，找到注册的 `KvServer` service，并调用对应方法。

6. `KvServer::PutAppend/Get`
   把客户端请求转成 `Op`，调用 `m_raftNode->Start(op, ...)`。

7. `Raft::Start`
   如果本节点是 leader，则把 `Op` 序列化后追加到 leader 的 `m_logs`。

8. `Raft::leaderHearBeatTicker` -> `Raft::doHeartBeat` -> `Raft::sendAppendEntries`
   leader 周期性把日志发给 follower。

9. 多数派复制成功后，leader 更新 `m_commitIndex`。

10. `Raft::applierTicker`
    把 `m_lastApplied < m_commitIndex` 的日志包装成 `ApplyMsg` 推给 `applyChan`。

11. `KvServer::ReadRaftApplyCommandLoop`
    从 `applyChan` 取出已提交命令，调用 `GetCommandFromRaft`。

12. `KvServer::GetCommandFromRaft`
    对 `Put/Append` 做去重后执行到跳表，并通过 `waitApplyCh[raftIndex]` 唤醒正在等待的客户端 RPC handler。

这条链路读通后，整个项目就有骨架了。

## 4. 第二条主线：Raft 选举

建议按下面顺序读：

1. `raft.h` 中的核心状态：
   `m_currentTerm`、`m_votedFor`、`m_logs`、`m_commitIndex`、`m_lastApplied`、`m_nextIndex`、`m_matchIndex`、`m_status`。

2. `Raft::init`
   初始化状态，读取持久化数据，启动心跳、选举、apply 三个循环。

3. `Raft::electionTimeOutTicker`
   根据随机选举超时时间判断是否发起新一轮选举。

4. `Raft::doElection`
   转为 Candidate，任期加一，投自己，向其他节点发 `RequestVote`。

5. `Raft::RequestVote`
   follower 处理投票请求：任期检查、日志新旧检查、是否已经投过票。

6. `Raft::sendRequestVote`
   candidate 收到投票响应后统计多数派，多数通过则转为 leader，初始化 `nextIndex/matchIndex`，立刻发送心跳。

读这一段时要一直问三个问题：

- 什么时候必须降级为 Follower？
- 哪些字段变化后必须 `persist()`？
- 为什么判断 candidate 日志是否 up-to-date？

## 5. 第三条主线：日志复制与提交

核心文件仍然是 `raft.cpp`。

1. `Raft::Start`
   只有 leader 会接受上层命令，把命令追加到本地日志并返回预期 log index。

2. `Raft::doHeartBeat`
   对每个 follower 构造 `AppendEntriesArgs`。这里的 `AppendEntries` 既是心跳，也是日志复制。

3. `Raft::getPrevLogInfo`
   根据每个 follower 的 `nextIndex` 决定 `PrevLogIndex/PrevLogTerm`。

4. `Raft::AppendEntries1`
   follower 处理日志复制：
   - 拒绝过期 term。
   - 接受更新的 term 并转 follower。
   - 检查 `PrevLogIndex/PrevLogTerm` 是否匹配。
   - 追加或覆盖冲突日志。
   - 根据 leader commit 更新自己的 `m_commitIndex`。

5. `Raft::sendAppendEntries`
   leader 处理 follower 响应：
   - 响应 term 更大则降级。
   - 失败则回退该 follower 的 `nextIndex`。
   - 成功则更新 `matchIndex/nextIndex`。
   - 多数派复制当前任期日志后推进 `m_commitIndex`。

6. `Raft::applierTicker` 和 `Raft::getApplyLogs`
   把已提交但尚未 apply 的日志交给 KV 层。

重点理解一个细节：代码里既有“逻辑日志下标”也有 `m_logs` vector 的“物理下标”。快照会截断前缀日志，所以要通过 `m_lastSnapshotIncludeIndex` 和 `getSlicesIndexFromLogIndex` 做转换。

## 6. 第四条主线：快照与持久化
//持久化由raft执行，如果持久化状态太大就由kvserver层制作快照，最后由Raft::Snapshot进行持久化
相关文件：

- `Persister.cpp`
- `Raft::persist/persistData/readPersist/Snapshot/InstallSnapshot`
- `KvServer::MakeSnapShot/ReadSnapShotToInstall/GetSnapShotFromRaft/IfNeedToSendSnapShotCommand`
- `SkipList::dump_file/load_file`

阅读顺序：

1. `Raft::persistData`
   看哪些 Raft 字段会被保存：term、votedFor、快照边界、日志。

2. `Persister::SaveRaftState` 和 `Persister::Save`
   区分只保存 RaftState 和同时保存 RaftState + Snapshot。

3. `KvServer::IfNeedToSendSnapShotCommand`
   当 Raft 状态大小超过阈值时，由 KvServer层制作快照并调用 `Raft::Snapshot`。

4. `Raft::Snapshot`
   Raft 丢弃已经进入快照的日志前缀，并保存上层传来的 snapshot 字节串。

5. `Raft::leaderSendSnapShot` 和 `Raft::InstallSnapshot`
   当 follower 的 `nextIndex` 落在 leader 快照之前，leader 改发快照。

6. `KvServer::ReadSnapShotToInstall`
   KV 层反序列化快照，恢复跳表和 `m_lastRequestId`。

要特别注意：Raft 层不理解 KV 快照内容，只负责保存和传输字节串；快照格式由 `KvServer` 决定。

## 7. 第五条主线：RPC 框架

读 RPC 时建议先看示例，再看框架：

1. `example/rpcExample/friend.proto`
2. `example/rpcExample/callee/friendService.cpp`
3. `example/rpcExample/caller/callFriendService.cpp`
4. `src/rpc/rpcheader.proto`
5. `src/rpc/mprpcchannel.cpp`
6. `src/rpc/rpcprovider.cpp`

理解重点：

- protobuf 的 `option cc_generic_services = true` 会生成 service 和 stub。
- 调用方拿到的是 stub，stub 最终走到 `MprpcChannel::CallMethod`。
- 服务方用 `RpcProvider::NotifyService` 注册 service 对象。
- 请求包格式是：`[varint header_size] + ]serialized RpcHeader] + ]serialized args]`。
- `RpcProvider::OnMessage` 根据 `service_name/method_name` 找到本地方法并调用。

读懂这层后，再回头看 `RaftRpcUtil` 和 `raftServerRpcUtil` 会很轻松，因为它们只是把 stub 包了一层。

## 8. 第六条主线：协程模块

协程模块对主线不是必须，但理解它能解释为什么 Raft 的定时器这样启动。

建议阅读顺序：

1. `fiber.hpp/cpp`
   协程对象、状态、`resume/yield`。

2. `scheduler.hpp/cpp`
   调度器如何管理函数任务或协程任务。

3. `timer.hpp/cpp`
   定时器集合。

4. `iomanager.hpp/cpp`
   epoll、pipe tickle、IO 事件和定时器结合。

5. `hook.cpp`
   sleep/socket/connect 等系统调用 hook。

回到 Raft 时只需要定位 `Raft::init`：

```cpp
m_ioManager = std::make_unique<monsoon::IOManager>(FIBER_THREAD_NUM, FIBER_USE_CALLER_THREAD);
m_ioManager->scheduler([this]() -> void { this->leaderHearBeatTicker(); });
m_ioManager->scheduler([this]() -> void { this->electionTimeOutTicker(); });
```

也就是说，选举和心跳定时循环由 IOManager 调度，apply 循环单独开线程。




## 10. 建议打断点或加日志的位置

如果你用 gdb 或日志跟踪，优先看这些位置：

- `Clerk::PutAppend`：观察客户端如何切换 leader。
- `KvServer::PutAppend`：观察请求如何进入 Raft。
- `Raft::Start`：观察只有 leader 会追加日志。
- `Raft::doElection`：观察选举开始。
- `Raft::RequestVote`：观察投票被接受或拒绝的原因。
- `Raft::doHeartBeat`：观察 leader 给每个 follower 发送的日志区间。
- `Raft::AppendEntries1`：观察 follower 如何处理日志冲突。
- `Raft::sendAppendEntries`：观察 `nextIndex/matchIndex/commitIndex` 的变化。
- `Raft::applierTicker`：观察日志提交后何时交付给 KV 层。
- `KvServer::GetCommandFromRaft`：观察状态机执行和去重。

## 11. 容易混淆的点

1. `AppendEntries` 不只是心跳。
   当 `entries` 为空时是心跳；有日志时就是日志复制。

2. `logIndex` 不等于 `m_logs` 的 vector 下标。
   快照会截断日志前缀，所以要用 `getSlicesIndexFromLogIndex` 转换。

3. `Get` 也会进入 Raft。
   这是为了读请求也经过一致性顺序，避免读到旧 leader 的过期状态。

4. 客户端重试不会简单地产生重复写。
   `ClientId + RequestId` 会被 KV 层记录在 `m_lastRequestId`，`Put/Append` apply 时会做去重。

5. `waitApplyCh` 是 KV 层等待某个 Raft index 被提交的临时通道。
   客户端 RPC handler 提交命令后会等待对应 index；Raft apply 后，KV 层用同一个 index 唤醒它。

6. Raft 层不解析业务命令。
   对 Raft 来说 `Command` 只是字符串；真正解释 `Op` 的是 `KvServer`。

7. 快照内容属于 KV 层。
   Raft 只知道 snapshot 是字节串，不知道里面有跳表数据和请求去重表。

8. `.pb.h/.pb.cc` 很长但不是第一阅读重点。
   先读 `.proto`，只在需要确认 generated API 时跳进生成文件。

9. `test` 目录不是系统性测试。
   它更像语言特性和工具函数实验区。

10. 当前代码调试输出很多。
    `src/common/include/config.h` 里的 `Debug` 会影响日志量，阅读运行输出时先接受它会比较吵。

## 12. 建议的阅读任务清单

可以按下面的小任务推进：

1. 跑起 3 节点集群和一个客户端，观察 `Put/Get` 成功。
2. 在 `Raft::Start` 打日志，确认只有 leader 接收客户端命令。
3. 在 `Raft::doElection` 和 `Raft::RequestVote` 打日志，观察 term 和 votedFor。
4. 在 `Raft::sendAppendEntries` 打日志，观察多数派复制后 commitIndex 推进。
5. 在 `KvServer::GetCommandFromRaft` 打日志，确认状态机只执行已提交命令。
6. 人为杀掉一个节点进程，观察客户端是否能继续通过多数派完成请求。
7. 调小 `m_maxRaftState` 或快照阈值，观察 `Snapshot/InstallSnapshot` 路径。
8. 单独运行 `example/rpcExample`，确认 RPC 框架的 service/stub 调用模型。
9. 单独阅读 `example/fiberExample`，确认协程调度器的基本行为。

读完这些，你就能解释项目的完整主链路。之后再补 `src/rpc`、`src/fiber`、`src/skipList`，属于把“能讲清楚”推进到“能改得动”。
