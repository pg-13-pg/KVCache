# KVCache 测试验证说明

本文记录 KVCache 当前已经具备的测试验证能力、测试目标、模拟场景、执行方式和已完成的验证结果。

## 1. 测试范围

当前测试覆盖以下几类功能：

| 测试类别 | 主要验证内容 |
| --- | --- |
| 命令行和基础功能测试 | `raftNode`、`kvctl` 的帮助信息和非法参数处理 |
| 数据结构和工具测试 | Skip List 快照、序列化、格式化、延迟队列、线程 join、调度器协作休眠 |
| 持久化测试 | WAL 写入、读取、尾部恢复以及快照策略 |
| Raft 单元测试 | AppendEntries、故障策略、节点配置、状态协议 |
| RPC 测试 | RPC 帧编解码、客户端和服务端请求传输 |
| Raft 集成测试 | Leader 选举、Leader 故障转移、节点重启、快照恢复、日志追赶和传输故障 |
| Sanitizer 测试 | ASan 内存越界/释放错误和泄漏、UBSan 未定义行为、TSan 数据竞争 |
| 业务场景测试 | 持续并发读写、Leader 进程终止、自动重新选主、节点 WAL/快照恢复、网络延迟、丢包和最终一致性 |

## 2. CTest 测试

CTest 会执行构建系统注册的测试目标，并报告每个目标的退出码和耗时。它验证的是“测试程序是否按预期结束”，不是对整个项目做形式化正确性证明。

常用命令：

```bash
ctest --test-dir cmake-build-debug --output-on-failure
```

出现失败时，`--output-on-failure` 会显示失败测试的标准输出和错误输出。当前项目的测试目标包括命令行测试、基础库测试、WAL/快照测试、RPC 测试、Raft 单元测试和 6 个 Raft 集成场景。

## 3. Sanitizer 验证

项目分别使用独立构建目录运行 Sanitizer：

```bash
setarch "$(uname -m)" -R ctest --test-dir cmake-build-asan --output-on-failure
setarch "$(uname -m)" -R ctest --test-dir cmake-build-ubsan --output-on-failure
TSAN_OPTIONS=halt_on_error=1:second_deadlock_stack=1 \
  setarch "$(uname -m)" -R \
  ctest --test-dir cmake-build-tsan --output-on-failure
```

其中 `setarch ... -R` 用于规避当前环境下 ThreadSanitizer 的地址映射限制。它不是项目逻辑的一部分，而是测试环境兼容性设置。

Sanitizer 通过表示在本次测试输入和执行路径下没有检测到对应类别的运行时问题，不代表所有输入、所有线程交错和所有内存生命周期都已经被穷尽验证。

## 4. 业务场景脚本

脚本 `scripts/run_scenario_suite.py` 将业务负载和故障注入串联起来，主要流程如下：

1. 启动 3 个 Raft 节点，并等待初始 Leader。
2. 使用 `kvbench` 执行持续并发读写。
3. 强制终止当前 Leader 进程，验证剩余节点重新选举。
4. 在新 Leader 上继续执行并发读写。
5. 重启被终止的节点，验证从独立数据目录中的 WAL/快照恢复并重新加入集群。
6. 注入 AppendEntries 网络延迟。
7. 注入 AppendEntries 丢包，观察预期的失败和超时。
8. 清除故障策略，等待副本收敛，并写入/读取验证键。

默认情况下，脚本会在 `logs/scenario-YYYYMMDD-HHMMSS/` 中保存：

- `events.log`：阶段、进程、Leader 和故障事件
- `status.log`：各节点定期的 term、role、commit index、last applied
- `node-*.log`：每个 Raft 节点的详细运行日志
- `kvbench.log`：客户端吞吐、成功数、失败数、超时数和延迟统计
- `summary.txt`：最终验证摘要

## 5. 本次 5 分钟测试

执行命令：

```bash
python3 -u scripts/run_scenario_suite.py \
  --duration 300 \
  --recovery-duration 30 \
  --fault-duration 30 \
  --threads 4 \
  --keyspace 100000 \
  --value-size 256 \
  --read-ratio 70 \
  --timeout-ms 1000 \
  --verify-keys 100
```

本次运行目录为：

```text
/root/KVCache/logs/scenario-20260904-200950
```

### 5.1 阶段结果

| 阶段 | 结果 |
| --- | --- |
| 初始选举 | `node2` 成为 Leader，`term=1` |
| 第一个 300 秒并发阶段 | 约 31,614 次操作，`failure=0`，`timeout=0` |
| Leader 故障 | 强制终止 `node2` 进程 |
| 故障转移 | `node0` 在 `term=2` 成为新 Leader，约 1 秒完成 |
| 第二个 300 秒并发阶段 | 约 30,407 次操作，`failure=0`，`timeout=0` |
| 节点恢复 | `node2` 重启并重新加入集群，恢复阶段约 3,209 次操作，`failure=0` |
| 恢复后收敛 | `replicas_converged=True` |
| 网络延迟 | 注入 `AppendEntries delay 200ms`，约 3,099 次操作，`failure=0`，`timeout=0` |
| 丢包 | 注入 `AppendEntries drop`，约 2,315 次操作，8 次预期超时 |
| 最终验证 | 100 个验证键全部读回成功，3 个副本最终收敛 |

### 5.2 任期和角色变化

事件日志记录了以下关键状态变化：

```text
initial_leader=node2 term=1
leader_down=node2 term=1 role=LEADER
replacement_leader=node0 term=2
restarted_node=node2
final node0:FOLLOWER/t12/c91181/a91181
final node1:FOLLOWER/t12/c91181/a91181
final node2:LEADER/t12/c91181/a91181
```

最终摘要为：

```text
verification_keys=100/100
replicas_converged=true
final_nodes=3/3
```

### 5.3 本次测试结论

在本次测试配置、机器环境和执行时间范围内，可以确认：

- 3 节点集群能够完成初始 Leader 选举。
- Leader 进程被强制终止后，剩余节点能够重新选举并继续处理请求。
- 被终止节点能够通过原数据目录恢复，并重新追赶集群日志。
- 200ms AppendEntries 延迟不会导致本次业务请求失败或超时。
- AppendEntries 丢包会造成部分请求超时，但清除故障后副本能够恢复并最终收敛。
- 最终 100 个验证键全部写入并读回成功，3 个节点的 commit index 和 last applied 最终一致。

## 7. 验证边界

上述测试说明当前实现具备一定的功能测试、故障模拟和一致性验证能力，但不能单独证明项目“完全没有问题”。尚未由这套测试充分覆盖的内容包括：

- 更高线程数、更大数据量和更长时间运行下的稳定性。
- 磁盘满、磁盘损坏、WAL 部分写入和文件系统异常。
- 同时终止两个节点、网络分区以及跨机房网络条件。
- 进程崩溃时所有线程和连接的资源回收。
- 极端消息乱序、重复 RPC、时钟跳变和系统负载抖动。
- 长期运行时的内存增长、文件增长和性能退化。
- 生产环境部署、权限、监控、备份和升级回滚流程。

因此，当前结论应表述为：**项目核心功能和已设计的故障场景在本次测试环境中验证通过，但仍需要更广泛的压力、故障注入、长期稳定性和生产环境测试。**
