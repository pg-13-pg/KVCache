# 分布式系统优化调研与建议

本调研基于 GitHub 官方仓库和设计资料，重点比较高 Star 的 Raft、分布式 KV 和存储系统，并结合 KVCache 当前实现提出优化建议。Star 会持续变化，文中的数量为检索时的近似值。

## 推荐重点参考的项目

| 项目 | 约 Star | 主要借鉴方向 |
| --- | ---: | --- |
| [etcd](https://github.com/etcd-io/etcd) | 52k+ | Raft、一致性 KV、WAL、快照、成员变更、故障恢复 |
| [RocksDB](https://github.com/facebook/rocksdb) | 32k+ | C++ LSM 存储、WAL、MemTable、Compaction、缓存 |
| [TiKV](https://github.com/tikv/tikv) | 16k+ | Region 分片、多 Raft Group、自动迁移、PD 调度 |
| [CockroachDB](https://github.com/cockroachdb/cockroach) | 高热度 | Range 分片、Leaseholder、热点拆分、自动 Rebalance |
| [FoundationDB](https://github.com/apple/foundationdb) | 16k+ | ACID 事务、角色分离、事务协调和故障恢复 |

建议阅读顺序：etcd 解决 Raft 正确性和运维问题；RocksDB 优化本地持久化；TiKV 学习多分片 Raft；CockroachDB 学习热点与负载均衡；FoundationDB 研究多 Key 事务。

## 当前代码中的优先瓶颈

### SkipList 的全局锁

当前跳表使用单一 std::mutex，读写请求可能竞争同一把锁。[skipList.h](/home/siuk/KVCache/src/skipList/include/skipList.h:123)

建议先用读写锁，再按 shard/key-range 拆分锁，并使用 perf 或火焰图确认锁竞争。

### RPC 单连接串行化

MprpcChannel 对共享 socket 使用 m_callMutex，单个连接上的请求响应被串行化。[mprpcchannel.cpp](/home/siuk/KVCache/src/rpc/mprpcchannel.cpp:68)

建议使用连接池、多个独立 channel、request ID 响应匹配、异步 RPC 或 Pipeline。

### 构建路径固定

CMake 固定从 /usr/local/include 和 /usr/local/lib 查找依赖，并把产物输出到项目级 bin/、lib/。[CMakeLists.txt](/home/siuk/KVCache/CMakeLists.txt:11)

建议使用 find_package、target 级别依赖和独立 Debug/Release/ASan 输出目录。

## P0：稳定性和正确性

1. 明确读一致性：提供 LinearizableRead、ReadIndex、LocalRead 三种模式，默认 kvctl get 使用强一致读。可参考 [etcd](https://github.com/etcd-io/etcd)。
2. 请求幂等：为写请求增加 client_id + request_id，服务端保存最近请求结果，防止客户端重试导致重复写入。
3. 完善 WAL 和 Snapshot：确保 WAL 持久化、多数副本提交、状态机 Apply、返回成功的顺序；增加校验和、临时文件原子 rename、损坏检测和磁盘空间保护。
4. 超时、重试和背压：设置连接超时、请求超时、重试上限、指数退避、pending proposal 上限和队列满快速失败。
5. 成员变更：实现 Joint Consensus，并支持 Learner 节点先同步日志再转正式副本。

## P1：并发和吞吐量

1. 批量 RPC 和批量提交：增加 BatchPut、BatchGet、BatchDelete、Raft Entry Batch、WriteBatch、Pipeline，并限制批量的条数、字节数和等待时间。
2. 线程流水线解耦：

    RPC/EventLoop -> Request Queue -> Raft Propose -> Commit Queue -> State Machine Apply -> Response Queue

网络线程不要执行磁盘写入、快照和大批量 Apply。

3. 缓存：采用客户端缓存、节点热点缓存、Block Cache、磁盘的分层结构，并设计 TTL、版本号或 Watch 失效机制。
4. 本地存储升级：抽象 Storage 接口，提供 MemoryStorage、现有文件存储和 RocksDBStorage。参考 [RocksDB](https://github.com/facebook/rocksdb) 的 WAL、WriteBatch、Block Cache、Bloom Filter 和 Compaction。
5. 连接复用：避免每次请求建立 TCP 连接；对大 Value 使用流式传输。

## P2：突破单 Leader 并发上限

如果所有 Key 共享一个 Raft Group，写入会集中到一个 Leader、一个日志和一个状态机。长期应演进为：

Key -> Shard/Region -> 独立 Raft Group -> Leader -> 本地存储

TiKV 使用 Region 和多个 Raft Group，CockroachDB 使用 Range 和多个 Raft 副本。[TiKV](https://github.com/tikv/tikv)、[CockroachDB](https://github.com/cockroachdb/cockroach)

推荐路线：

1. 先实现固定 Hash 分片；
2. 每个分片独立维护 Raft 状态；
3. 增加路由和元数据；
4. 实现副本迁移、热点 Split 和自动 Rebalance；
5. 最后考虑 Range 分片和跨分片事务。

## 稳定性和可观测性

建议增加 Prometheus 指标：

- Raft Term、Leader、Commit Index、Apply Index；
- AppendEntries 延迟和失败数；
- 选举次数、Leader 变更次数；
- Snapshot 生成/安装耗时；
- RPC QPS、错误率、重试数；
- KV P50/P95/P99 延迟；
- WAL fsync 延迟、Compaction 压力；
- 磁盘剩余空间和 Follower 复制延迟。

当前项目已经有多节点故障转移、重启、Snapshot、WAL 和传输故障集成测试。[test/CMakeLists.txt](/home/siuk/KVCache/test/CMakeLists.txt:90)

下一步应增加性能测试：单节点和三节点、1/5/20/100 个并发客户端、纯读/纯写/50-50 混合、1 KB/16 KB/1 MB Value，并记录 QPS、P99 延迟、CPU、磁盘 IO、fsync 和复制延迟。

## 故障测试

建议覆盖 Leader/Follower 终止、网络延迟/丢包/分区、磁盘写入失败、空间不足、Snapshot 损坏、RPC 超时、节点重启、重复请求和成员变更期间宕机。

除了检查进程不崩溃，还要验证：

- 始终只有一个 Leader；
- 已提交数据不丢失；
- 未提交数据不会被错误应用；
- 节点恢复后自动追平；
- 客户端能重新定位 Leader；
- 不出现数据分叉或状态机不一致。

## 建议落地路线

### 阶段 1：单分片稳定化

补齐 WAL/Snapshot 恢复、线性一致读、请求去重、超时重试、Leader 重定向、指标和故障测试。

### 阶段 2：存储引擎升级

评估 RocksDB、WriteBatch、Block Cache、Bloom Filter、后台 Flush/Compaction 和存储损坏恢复。

### 阶段 3：多分片

定义 Shard/Region 元数据，实现独立 Raft、Key 路由、Split/Merge、副本迁移和自动负载均衡。

### 阶段 4：事务和高级能力

实现 Multi-Key 原子操作、MVCC、事务冲突检测、跨分片事务、备份恢复和多机房故障域感知。

## 最值得优先实现的五项

1. 批量 RPC、批量 Raft Append 和 WriteBatch；
2. RPC 连接池或异步多路复用；
3. 请求幂等、超时退避和背压；
4. WAL/Snapshot 校验与恢复增强；
5. 多 Raft Group 分片。

核心结论：增加线程只能缓解部分问题，真正突破并发上限需要“批处理 + 减少锁竞争 + 本地 LSM 存储 + 多 Raft Group 分片”。
